# CLAUDE CODE IMPLEMENTATION PROMPT — UMODZI CONNECT

## Theme B: Navy + Teal + Coral — CANONICAL LIVE PRODUCT DESIGN SYSTEM

### Reusable UI Design System, Landing Page, Authentication and Application-Wide Styling

## 1. Your Role

Act as a senior software engineer and UI/UX designer with at least 10 years of experience building production-ready web applications, service marketplaces, responsive dashboards and reusable design systems.

You are working on **Umodzi Connect**, a smart dispatch and trust-verification platform that connects consumers with verified skilled technicians in Zambia.

Implement the visual identity shown in the supplied **Navy + Teal + Coral reference image** throughout the existing application.

The reference image is the visual specification and establishes the canonical live design system for:

* Landing page
* Login page
* Registration page
* Consumer dashboard
* Technician dashboard
* Technician discovery and search
* Technician profiles
* Service request forms
* Dispatch and job tracking
* Navigation, cards, forms, buttons, dialogs and notifications

**Important:** Theme B is not inspiration. It is the canonical reusable UX/UI system for the live application. Reproduce its composition, proportions, typography hierarchy, button shapes, cards, navigation, authentication split, spacing, section transitions, technician cards, verification badges, search/filter patterns, mobile layout and dashboard language in real, functional, responsive application components. Do not introduce a different visual language on later screens.

Do not build a disconnected prototype. Work inside the existing project, preserve its functionality and integrate the design into its existing architecture.

## 2. Brand Identity

**Product name:** Umodzi Connect

**Tagline:** Skilled People. Stronger Communities.

**Product purpose:** Help people discover trusted technicians, request services, and track technician assignments through skill-based matching, location awareness and transparent trust signals.

The interface should feel:

* Modern and professionally engineered.
* Friendly and community-oriented.
* Trustworthy without appearing like a banking application.
* Technically capable without looking like a generic AI dashboard.
* Appropriate for Zambia, particularly the initial Kitwe and Ndola service areas.
* Comfortable to use on mobile phones, laptops and desktop computers.
* Lightweight enough for users with limited mobile data and slower internet connections.

Avoid generic AI-generated SaaS styling, excessive gradients, excessive glassmorphism, random decorative icons, unnecessary animation, oversized empty spaces and repetitive template-like cards.

The identity should be recognizable even when the logo is absent.

## 3. Official Color System

Use the following as the initial design tokens. Centralize them so the entire application uses the same values.

| Token            | Hex       | Purpose                                                               |
| ---------------- | --------- | --------------------------------------------------------------------- |
| Primary Navy     | `#102A43` | Main branding, navigation, headings and primary structure             |
| Deep Navy        | `#082F3C` | Dark hero backgrounds, deep surfaces and selected navigation states   |
| Primary Teal     | `#00A6A6` | Main interactive accents, location indicators and selected controls   |
| Deep Teal        | `#007F83` | Hover states, stronger teal surfaces and emphasis                     |
| Coral            | `#FF6B6B` | Important calls to action, secondary emphasis and selected highlights |
| Light Background | `#F5F8FA` | Main application background                                           |
| White            | `#FFFFFF` | Cards, forms and elevated surfaces                                    |
| Primary Text     | `#243746` | Body text and labels                                                  |
| Muted Text       | `#647786` | Supporting text and secondary information                             |
| Border           | `#DCE5EA` | Input borders, card outlines and dividers                             |
| Success          | `#16845B` | Verified states, completed jobs and successful actions                |
| Warning          | `#D99100` | Pending states and warnings                                           |
| Error            | `#C83E4D` | Errors, failed requests and destructive actions                       |

Do not use all colors with equal intensity.

Apply the colors according to their semantic roles:

* Navy establishes the brand and visual structure.
* Teal communicates interaction, location, navigation and progress.
* Coral attracts attention to important actions.
* White and light backgrounds maintain readability.
* Success, warning and error colors communicate status independently of branding.

Use white text on dark surfaces and sufficiently dark text on light surfaces. Check contrast before finalizing buttons, labels, badges and navigation items.

Create a shared theme definition using the styling system already installed in the project. If CSS variables are appropriate, establish tokens such as:

```css
:root {
  --color-primary: #102A43;
  --color-primary-deep: #082F3C;
  --color-accent: #00A6A6;
  --color-accent-hover: #007F83;
  --color-highlight: #FF6B6B;

  --color-background: #F5F8FA;
  --color-surface: #FFFFFF;
  --color-text: #243746;
  --color-text-muted: #647786;
  --color-border: #DCE5EA;

  --color-success: #16845B;
  --color-warning: #D99100;
  --color-error: #C83E4D;

  --radius-card: 14px;
  --radius-control: 10px;

  --shadow-card: 0 4px 18px rgba(16, 42, 67, 0.07);
}
```

Adapt the syntax to the existing framework. Do not introduce a second styling system unnecessarily.

## 6. Landing Page — Match the Reference Image

The landing page is the main public introduction to Umodzi Connect.

It should follow the reference image's dark, visually rich hero layout, with a strong text area, technician photography, location-based service discovery and a clear call to action.

### A. Header

Create a responsive public header with:

* Umodzi Connect logo on the left.
* Home.
* Services.
* How It Works.
* About.
* Login.
* Get Started.

On desktop, display the navigation horizontally.

On mobile, use a compact header and accessible mobile navigation.

Use navy for the header or its primary structure, teal for active navigation and coral for the primary Get Started action.

The header must remain readable over the hero area. If using a transparent header, ensure the text remains visible over the background image.

### B. Hero section

Create a large, responsive hero section with two visual areas.

**Text area:**

* Small introductory brand label.
* Large headline, for example: “Local Skills. Real Solutions.”
* Supporting text explaining that users can connect with verified technicians in Ndola, Kitwe and other supported locations.
* Trust indicators such as Verified Profiles, Smart Matching, Live Location and Trusted Reviews.
* Service search field.
* Search button.
* Primary CTA: “Find a Technician”.
* Secondary CTA: “Become a Technician”.

**Image area:**

* Large, high-quality photograph of a real-looking local technician.
* The image should feel authentic, professional and community-oriented.
* Use a balanced crop, clear subject placement and responsive sizing.
* Incorporate teal and coral accent shapes sparingly.
* Include subtle location-inspired graphics only when they improve the composition.

The hero should feel like a carefully art-directed marketplace website, not a generic landing-page template.

### C. Background image support — mandatory

The landing page MUST support a configurable background photograph, as demonstrated in the reference image.

Do not hardcode the hero image permanently into the JSX or component markup.

Implement a reusable hero component that accepts configuration properties similar to:

```tsx
type HeroSectionProps = {
  title: string;
  description: string;
  backgroundImage?: string;
  backgroundPosition?: string;
  overlayOpacity?: number;
  primaryActionLabel?: string;
  primaryActionHref?: string;
};
```

Adapt the interface to the project's actual language and conventions.

The background image should be changeable without redesigning the component.

Provide a central configuration source for the default hero content and image. The exact configuration format should follow the existing project architecture.

Requirements for image handling:

* Support an image URL or an existing local project asset.
* Allow a configurable image focal point, such as `center`, `center right` or `65% center`.
* Allow a configurable dark overlay so text remains readable.
* Use an appropriate `cover` crop and responsive positioning.
* Provide a sensible fallback when no image is configured or the image fails to load.
* Avoid layout shifts while images load.
* Use optimized images where the existing framework supports them.
* Keep meaningful alternative text for informative images.
* Respect mobile crop differences, including the ability to configure a different mobile image if needed.
* Avoid downloading large decorative images unnecessarily on mobile connections.

A suitable implementation may use CSS background images or a layered image element. Choose the approach that works best with the existing stack.

For example, the design may use a dark navy overlay over a technician photograph, with teal and coral accent elements. The photograph must remain visible rather than being completely obscured by a solid background.

**Future editing requirement:** Structure the hero configuration so an authorized administrator could eventually manage the image and hero copy through an existing content-management mechanism or a future settings interface. Do not build an unnecessary backend upload service unless the project already supports it or it is explicitly needed.

## 14. Typography, Spacing and Visual Hierarchy

Use the existing typography if it is already established and suitable. Otherwise, use a clean, modern sans-serif family such as Inter or Manrope.

Typography should distinguish:

* Large hero headings.
* Page titles.
* Section headings.
* Card titles.
* Body text.
* Supporting labels.
* Form labels and helper messages.

Use a consistent spacing scale rather than arbitrary margins throughout the project.

Recommended starting points:

* Main content spacing: 24–32 px on desktop.
* Card padding: 16–24 px.
* Form field spacing: 16–20 px.
* Card radius: approximately 14 px.
* Input radius: approximately 10 px.
* Button height: generally 44–48 px.

Adapt these values to the existing component library and actual screen sizes.

Avoid excessively rounded controls, oversized headings on every page and unnecessary shadows.

## 15. Mobile-First and Low-Data Requirements

Umodzi Connect targets users in Zambia, including people using smartphones and mobile data connections with varying reliability.

Therefore:

* Design mobile layouts deliberately rather than merely shrinking desktop pages.
* Use responsive breakpoints appropriate to the existing CSS framework.
* Keep navigation accessible on small screens.
* Ensure forms work with mobile keyboards.
* Optimize images and avoid unnecessary large downloads.
* Lazy-load below-the-fold imagery where appropriate.
* Avoid heavy animation and autoplay video.
* Respect reduced-motion preferences.
* Use lightweight icons and reuse existing assets.
* Prevent horizontal overflow.
* Provide meaningful loading, empty and error states.
* Ensure the primary service-request journey remains easy to complete on mobile.

Do not sacrifice accessibility or readability to achieve a compact layout.

## 16. Accessibility and Interaction States

Follow WCAG accessibility principles and the project's existing standards.

Ensure:

* Keyboard navigation works.
* Focus indicators are visible.
* Text and controls have sufficient contrast.
* Inputs have programmatically associated labels.
* Images have appropriate alternative text.
* Icon-only buttons have accessible names.
* Validation errors are identifiable without relying only on color.
* Dialogs manage focus correctly.
* Touch targets are comfortable on mobile.
* Buttons and links use the correct semantic elements.

Every visible interactive control must perform its intended action.

Do not create buttons, filters, tabs or navigation items that appear functional but have no implementation.

## 17. Technical Implementation Rules

Before editing any code:

1. Inspect the repository structure.
2. Identify the actual frontend framework, language, styling system and component library.
3. Identify the existing route structure and authentication flow.
4. Inspect current public pages, dashboards, forms and shared components.

However, **verify the actual repository before making stack-specific changes**. Do not migrate or replace the current stack just to implement this design.

Use the existing routing, authentication, API clients, data models and state management wherever possible.

Do not:

* Rebuild the application from scratch.
* Replace real API calls with mock data.
* Remove existing features.
* Change database schemas without a genuine requirement.
* weaken authorization or validation.

* create multiple competing theme files.

Keep the design tokens, logo, shared layouts and common components in predictable locations that match the existing repository conventions.
