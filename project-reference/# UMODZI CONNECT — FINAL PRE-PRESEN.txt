- Authentication and role-based dashboards.
- Customer and technician service workflows.
- Existing messaging/chat functionality.
- Existing SMS and Web Push notification functionality.
- Existing application branding and design system.
- Existing automated tests and integration tests.

## 3. PHASE TWO: DEEP CHAT FUNCTIONALITY AUDIT

This is a critical requirement.

Investigate the complete customer-to-technician messaging journey.

### A. Conversation creation and access

Verify that:

- Customers can access the correct conversations.
- Technicians can access the conversations associated with their assigned service requests.
- Conversations are correctly associated with the relevant service request where applicable.
- Users cannot access conversations belonging to other users.
- Conversation lists display the correct participants.
- Opening and navigating between conversations works.
- Direct navigation to a conversation works after refreshing the page.

Pay special attention to participant identification and role-based authorization on the backend.

### B. Message sending and receiving

Test the following:

- Sending a message as a customer.
- Receiving that message as the technician.
- Replying as the technician.
- Receiving that reply as the customer.
- Messages appearing without requiring a manual refresh.
- Messages being saved permanently in the database.
- Message history loading when a conversation is reopened.
- Correct sender identification.
- Correct message timestamps.
- Consistent chronological ordering.
- Long messages and multiline messages.
- Empty-message validation.
- Duplicate-message prevention.

A successful frontend button click is not proof of successful message delivery.

A message must only be marked as sent after the backend confirms successful persistence.

### C. Real-time communication and reconnection

Inspect the existing communication architecture.

If the application uses polling, WebSockets, server-sent events or an existing real-time provider, test the current implementation.

Do not introduce a new transport simply because it is fashionable.

Specifically verify:

- New messages reach the other participant within the expected interval.
- Connections or polling requests are cleaned up when leaving a conversation.
- Multiple open conversations do not create unnecessary requests.
- Messages are not duplicated after reconnection.
- Reconnection works after temporarily losing internet access.
- Existing polling intervals and retry strategies do not overload the backend.
- Message history remains consistent after reconnection.
- Failed sends are recoverable.
- Unsent messages are not falsely presented as delivered.

If WebSockets are used, examine authentication, origin validation, message authorization, input validation, payload limits and rate limiting.

### D. Read receipts and conversation state

Verify that:

- Unread messages are accurately counted.
- Reading a conversation updates its unread status.
- Read indicators are shown only when supported by actual backend state.
- Last-message previews update correctly.
- Conversation timestamps update correctly.
- Unread badges are accurate across dashboards.
- Notifications do not continue appearing unnecessarily for conversations currently being viewed.

Do not invent delivery or read statuses that the backend cannot substantiate.

### E. Chat security and privacy

Test whether:

- An unauthenticated visitor can retrieve messages.
- One customer can retrieve another customer's conversations.
- A technician can access conversations not assigned to them.
- Modifying conversation IDs exposes other users' messages.
- Invalid or oversized message content is accepted.
- Untrusted message content can execute HTML or JavaScript.
- Backend authorization is enforced independently of frontend navigation.

Respect the existing privacy design: administrators must not receive default access to private conversations simply because they have an administrative dashboard.

### F. Chat interface on mobile and desktop

Mobile:

- Conversation list is accessible.
- Opening a conversation uses the available screen space.
- Message bubbles remain readable.
- Message composer stays visible above the on-screen keyboard.
- Sending controls remain accessible.
- Scrolling to the latest message behaves correctly.
- Safe-area insets are respected.
- No message controls are hidden behind fixed navigation.

Desktop:

- Conversation list and conversation panel are appropriately arranged.
- Navigation between conversations is smooth.
- The message composer is properly positioned.
- Keyboard navigation works.
- Browser resizing does not break the layout.

### G. Required chat integration test

Use two genuinely authenticated user sessions:

SESSION A: Customer.

SESSION B: Technician.

Perform these steps:

1. Log in as the customer.
2. Open the relevant service conversation.
3. Log in as the assigned technician in a separate browser context.
4. Open the same conversation.
5. Send a customer message.
6. Confirm delivery and persistence on the technician side.
7. Reply as the technician.
8. Confirm delivery and persistence on the customer side.
9. Refresh both browser contexts.
10. Confirm that message history remains intact.
11. Disconnect one participant's internet connection.
12. Attempt a message send and verify the resulting status.
13. Restore connectivity.
14. Verify recovery and ensure no duplicate messages.
15. Test unread counts and read indicators.
16. Test access restrictions using a different authenticated user.

Record actual results.

Do not use mocked messages as proof of successful end-to-end communication.

## 4. PHASE THREE: PROGRESSIVE WEB APP AUDIT

Investigate the actual PWA implementation.

Use professional browser-platform guidance, including MDN Progressive Web Apps documentation, Chrome for Developers and WebKit documentation.

### A. Web application manifest

Inspect the manifest and verify:

- Application name.
- Short name.
- Stable application ID, where appropriate.
- Start URL.
- Application scope.
- Display mode.
- Theme colour.
- Background colour.
- 192 × 192 application icon.
- 512 × 512 application icon.
- Correct icon MIME types and file paths.
- Appropriate maskable icon support.
- Application description where applicable.

Ensure manifest values are consistent with the actual branding and production configuration.

Use existing logo assets. Never substitute unrelated logos.

A suitable installed application should use standalone display mode where supported, without sacrificing normal browser access.

### B. Service worker

Inspect the current service worker before changing anything.

Verify:

- Registration succeeds.
- Activation succeeds.
- Static application resources are cached appropriately.
- Offline fallback works.
- Outdated cache entries are managed.
- Application updates are handled correctly.
- No stale application version remains indefinitely.
- Failed asset requests are handled gracefully.
- Service-worker failures do not break the main application.

Do not create multiple competing service workers.

Do not indiscriminately cache authenticated API responses, private messages, authentication tokens or sensitive user information.

### C. Offline and network behaviour

Test:

- Normal connectivity.
- Slow connectivity.
- Temporarily interrupted connectivity.
- Complete offline mode.
- Recovery after reconnecting.
- Application reload while offline.
- Navigation while offline.

The application should provide a meaningful offline state.

Clearly distinguish:
- Online.
- Connecting.
- Offline.
- Reconnecting.
- Request failed.

Never tell users that a service request, message or payment succeeded when the server did not confirm it.

Do not introduce offline write queues unless they can be implemented with reliable synchronization, duplicate prevention and conflict handling.

### D. Installation experience

Check the installation experience across supported browsers.

Android:
- Verify Chrome installation eligibility.
- Confirm the correct app icon.
- Verify the installed application launches in standalone mode.
- Verify the launch screen is correctly branded.

iOS:
- Verify Safari Add to Home Screen instructions.
- Verify the app icon and installed launch behaviour.
- Check standalone navigation and safe-area handling.
- Do not assume Android installation APIs work on iOS.

Windows/Linux/macOS:
- Test installation using supported desktop browsers.
- Verify the application opens in a separate window where supported.
- Verify its title and icon.
- Confirm normal browser access remains functional.

Implement an installation control only when a supported installation mechanism is available.

Do not rely on the `beforeinstallprompt` event for iOS.

Do not create an intrusive installation popup that repeatedly interrupts users.

### E. Application updates

Verify that newly deployed application versions can reach users.

- Detect available service-worker updates.
- Avoid trapping users on old assets.
- Preserve authentication and unsent form data where possible.
- Avoid forcing disruptive reloads during active work.
- Provide an appropriate update notification when user action is required.
